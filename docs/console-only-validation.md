## 问题与修正

初版允许选择设备日志，并恢复了用户上次的 `captureMode=device`。该通道能读取 CoreFoundation、CoreBluetooth 等系统框架日志，但不能接管 LOOI 的 Swift.print / LIPrint。原窗口在搜索 KMP 时显示无匹配，这与用户需要替代 Xcode App 控制台的目标不符。

1. 移除采集方式选择、设备系统日志读取器及其自动重连路径。唯一新采集命令为 `devicectl device process launch --quiet --console --terminate-existing <Bundle ID>`，连接 App 的 stdout/stderr。
2. 不再读取或写入旧 captureMode 偏好。旧设备会话保留在数据库，但不进入工作区列表；本地导入文件仍可主动选择。
3. 采集设置只选择 iPhone 和 App，按钮明确显示「重启 App 并采集」，并说明会结束原 Xcode 调试会话。没有无提示的后台重启。
4. 新采集重置旧关键词、级别、ID 下界和搜索，避免 App 输出被设备分类筛选条件隐藏。重开先显示采集入口，不自动将旧会话当作当前结果。
5. quiet 去掉宿主工具的隧道、启动状态信息；App 自己写入标准流的 SDK 与业务内容不按关键词删减。
6. 停止时仅 SIGKILL 宿主读取器。等待双管道 EOF 与进程退出后归档，不再用固定延时猜测尾部已读完。
7. 补充 NSLog 时间戳与进程头识别，避免其被并入前一条 KMP 多行消息。

## 能力边界

已验证的是 App 标准输出与标准错误中的 print、业务打印、KMP 和 NSLog 格式消息；不声称与 Xcode 调试器所有输出逐字等价，不覆盖没有写入标准流的全部 Logger / Unified Logging、断点控制或原调试会话历史。普通 stdout 必须在启动时接管，无法事后附加由 Xcode 启动的既有进程。当前工具用明确的重启操作满足这一前提。
